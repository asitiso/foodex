# Foodex 코인 지갑과 꾸미기 상점 설계

## 목표

식사 기록에서 보여 주는 코인을 실제로 보유하고 사용할 수 있는 게임 자산으로 만든다. 사용자는 한 끼를 기록한 직후 코인을 받고, 현재 잔액을 확인하며, 캐릭터 방 꾸미기 상품을 구매할 수 있어야 한다.

이번 작업은 새 화면을 추가하지 않는다. 홈과 기존 친구·꾸미기 화면 안에 필요한 정보와 행동만 배치해 현재 디자인 밀도와 이동 구조를 유지한다.

## 사용자 경험

### 코인 획득

1. 식사 기록이 로컬 저장에 성공한다.
2. 기본 5코인을 획득한다.
3. 같은 날 두 번째 이후 식사라면 연속 식사 콤보로 3코인을 추가 획득한다.
4. 통합 보상 화면은 `+5` 또는 `+8` 코인을 보여 준다.
5. 동일한 식사 ID를 다시 저장해도 코인은 한 번만 지급한다.

저장 전에는 잔액을 올리지 않는다. 원격 연결이 끊긴 경우 로컬 원장에 먼저 기록하고, 기존 동기화 대기열을 통해 클라우드에 반영한다.

### 잔액 확인

홈 상단 레벨 표시 근처에 작은 코인 잔액을 둔다. 잔액은 상태 카드 하나를 추가하지 않고 기존 헤더 안에서 보조 정보로 표시한다.

친구 화면의 꾸미기 영역에서도 같은 잔액을 표시한다. 두 위치는 동일한 지갑 상태를 사용한다.

### 상품 구매

초기 상품은 네 개로 제한한다.

- 배경 2종
- 캐릭터 액세서리 2종

각 상품은 이미지 또는 기존 CSS 미리보기, 이름, 가격, 보유 상태를 표시한다. 상품을 선택하면 현재 캐릭터 방에 미리 적용하며, 구매를 확정하기 전까지 저장하지 않는다.

구매 성공 후 상품은 기존 옷장에 자동 등록되고 바로 적용할 수 있다. 이미 보유한 상품에는 구매 버튼 대신 `보유 중`을 표시한다.

잔액이 부족하면 구매 버튼을 짧게 흔들고 `N코인이 더 필요해요`를 표시한다. 별도 오류 팝업이나 새 경로는 만들지 않는다.

## 시각 설계

- 기존 크림 배경, 보라색 테두리, 노란색 보상 강조를 재사용한다.
- 코인 표시는 금색 원형 아이콘과 숫자만 사용한다.
- 상점은 기존 꾸미기 카드와 같은 모서리·그림자 값을 사용한다.
- 구매 가능한 상품 하나만 강조하고, 화면당 주요 행동은 하나로 유지한다.
- 구매 성공 시 상품 카드가 짧게 튀고 별가루가 나타난다.
- `prefers-reduced-motion` 또는 앱의 모션 감소 설정에서는 이동·흔들림을 제거하고 색과 테두리 변화만 사용한다.
- 320px 화면에서도 상품 이름, 가격, 버튼이 겹치지 않게 한 열 배치를 허용한다.

## 도메인 모델

### 코인 거래

코인 잔액을 직접 덮어쓰기만 하지 않고 거래 원장을 유지한다.

```ts
type CoinTransactionKind = 'meal-earned' | 'shop-spent'

interface CoinTransaction {
  id: string
  key: string
  kind: CoinTransactionKind
  amount: number
  mealId?: string
  productId?: string
  createdAt: number
}
```

- 획득 금액은 양수다.
- 사용 금액은 음수다.
- 식사 획득 키는 `meal:<mealId>:coins`다.
- 구매 키는 `shop:<purchaseId>:coins`다.
- 같은 키는 로컬과 원격에서 각각 한 번만 저장된다.
- 잔액은 거래 합계이며 0보다 작아질 수 없다.

### 상점 상품

상품 카탈로그는 코드에 고정된 정적 데이터로 관리한다.

```ts
interface ShopProduct {
  id: string
  type: 'background' | 'accessory'
  title: string
  price: number
  previewClass: string
}
```

초기 상품 수를 네 개로 제한해 운영 도구나 관리자 화면을 만들지 않는다.

## 로컬 저장

IndexedDB에 `coinTransactions` 저장소를 추가한다.

- 키: 거래의 안정적인 `key`
- 식사·카드·보상·코인 거래를 가능한 한 하나의 로컬 트랜잭션으로 저장한다.
- 재시도 시 `put`과 안정 키로 기존 거래를 교체하므로 중복되지 않는다.
- 지갑 잔액은 저장된 거래 합계로 계산한다.
- 구매는 잔액 확인, 지출 거래 저장, 상품 보상 저장을 하나의 로컬 트랜잭션에서 처리한다.

기존 사용자의 거래가 없을 때 잔액은 0으로 시작한다. 과거 식사에 코인을 소급 지급하지 않는다. 소급 계산은 사용자가 예상하지 못한 큰 잔액을 만들고 검증 비용이 높아 제외한다.

## Supabase 저장

기존 `profiles.coins`를 현재 잔액의 빠른 조회 값으로 사용하고, 새 `coin_transactions` 테이블을 원장으로 사용한다.

필수 열:

- `id uuid primary key`
- `user_id uuid not null`
- `transaction_key text not null`
- `kind text not null`
- `amount integer not null`
- `meal_id uuid null`
- `product_id text null`
- `created_at timestamptz not null`
- `unique (user_id, transaction_key)`

모든 행은 `auth.uid() = user_id`인 사용자만 조회할 수 있다. 클라이언트가 임의 금액을 직접 삽입해 잔액을 조작하지 못하도록 원장 쓰기는 공개 테이블 직접 삽입 대신 제한된 데이터베이스 함수로 처리한다.

### 원자적 획득

`claim_meal_coins(meal_id, transaction_key)` 함수는 다음을 한 트랜잭션에서 수행한다.

1. 현재 인증 사용자 소유의 식사인지 확인한다.
2. 해당 사용자의 같은 날짜 식사 수를 서버에서 계산한다.
3. 첫 식사는 5코인, 두 번째 이후 식사는 8코인으로 서버가 금액을 결정한다.
4. 거래 키가 없다면 원장에 삽입한다.
5. 새 거래인 경우에만 `profiles.coins`를 증가시킨다.
6. 지급 금액과 최종 잔액을 반환한다.

### 원자적 구매

`purchase_shop_product(product_id, transaction_key)` 함수는 서버에 정의된 상품과 가격만 허용한다.

1. 상품 ID와 가격을 검증한다.
2. 이미 보유한 상품인지 확인한다.
3. 잔액이 충분한지 확인한다.
4. 지출 원장, `profiles.coins` 감소, `user_rewards` 상품 등록을 한 트랜잭션에서 처리한다.
5. 최종 잔액과 보상 정보를 반환한다.

함수는 인증 사용자 ID를 내부에서 사용하고 외부 `user_id` 인자를 받지 않는다. 실제 원장 변경 함수는 `private` 스키마의 `SECURITY DEFINER` 함수로 만들고 고정된 `search_path`와 명시적인 `auth.uid()` 검증을 사용한다. `PUBLIC` 실행 권한은 제거하고 `authenticated`에만 실행 권한을 부여한다. Data API가 호출하는 `public` 함수는 `SECURITY INVOKER` 래퍼로 제한하며, 금액이나 사용자 ID를 임의로 전달하지 않고 검증된 비공개 함수만 호출한다.

기존 `user_rewards` 제약에는 상점 출처가 없으므로 `source_type`에 `shop`을 추가한다. 액세서리는 기존 보상 타입과 UI 적용 구조를 재사용할 수 있는 범위에서 `skin`으로 저장하고, 상품 ID로 외형을 구분한다.

## 동기화

- 로컬 저장 성공은 원격 응답을 기다리지 않는다.
- 동기화 대기 항목에 코인 거래 키를 포함한다.
- 원격 동기화는 식사·카드 업로드 뒤 식사 코인을 청구한다.
- 동일 키가 이미 원격에 있으면 성공으로 처리하고 최종 잔액을 받아 로컬 표시를 조정한다.
- 구매는 잔액 부족 여부가 중요한 작업이므로 온라인 상태에서 원격 원자적 구매를 먼저 확정한다.
- 오프라인에서는 상품 미리보기는 허용하지만 구매 버튼에 `연결 후 구매할 수 있어요`를 표시한다. 오프라인 구매 예약은 이중 구매와 잔액 충돌을 만들 수 있어 지원하지 않는다.

## 오류 처리

- 식사 코인 원격 반영 실패: 기록과 로컬 코인은 유지하고 동기화 상태로 안내한다.
- 구매 중 연결 실패: 잔액과 보유 상품을 변경하지 않고 다시 시도 버튼을 유지한다.
- 잔액 부족: 부족한 코인 수를 표시한다.
- 이미 보유: 성공 상태로 정규화하고 옷장에 상품을 표시한다.
- 프로필이 없는 익명 사용자: 원격 함수가 프로필을 안전하게 생성한 후 처리한다.

## 테스트

### 도메인

- 기본 식사는 5코인, 콤보 식사는 8코인이다.
- 같은 식사 키는 한 번만 합산된다.
- 지출 후 잔액이 정확하다.
- 잔액 부족 구매는 거절된다.

### 로컬 저장

- 식사 재시도에서 코인 거래가 중복되지 않는다.
- 구매가 지출과 보상을 함께 저장한다.
- 중간 실패 시 지출과 보상이 모두 저장되지 않는다.

### Supabase

- 획득 함수가 같은 거래 키를 두 번 반영하지 않는다.
- 다른 사용자의 식사로 코인을 받을 수 없다.
- 클라이언트가 지급 금액을 임의로 지정할 수 없다.
- 구매 함수가 음수 잔액을 만들지 않는다.
- 다른 사용자의 거래를 조회할 수 없다.
- 보안 및 성능 어드바이저를 실행한다.

### 화면

- 홈과 꾸미기 화면이 같은 잔액을 표시한다.
- 구매 전 미리보기는 저장 상태를 바꾸지 않는다.
- 성공한 구매가 옷장에 나타난다.
- 잔액 부족과 오프라인 상태가 이해 가능한 문구로 나타난다.
- 모션 감소 설정에서 구매 모션이 제거된다.

## 완료 기준

- 한 끼 저장 후 코인 잔액이 즉시 증가한다.
- 같은 식사를 다시 저장해도 잔액이 증가하지 않는다.
- 새로고침 후 로컬 잔액이 유지된다.
- 로그인 사용자는 다른 기기에서도 원격 잔액과 구매 상품을 복원할 수 있다.
- 구매가 잔액과 보유 상품을 원자적으로 변경한다.
- 기존 기록, 카드, 보상, 오프라인 동기화 테스트가 모두 통과한다.
- Supabase RLS와 함수 권한 검증이 통과한다.
- `npm.cmd run test:run`과 `npm.cmd run build`가 성공한다.

## 제외 범위

- 코인 유료 구매
- 환불과 상품 회수
- 기간 한정 가격
- 랜덤 뽑기
- 선물과 사용자 간 거래
- 관리자 상품 편집 화면
- 과거 식사 코인 소급 지급
