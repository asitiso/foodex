# Foodex V3 세계 수집 업데이트 설계

## 목표

Foodex V2의 식사 기록·카드 수집 루프를 지역, 계절, 세트, 퓨전, 꾸미기 콘텐츠로 확장한다. 사용자는 별도 관리 작업 없이 식사를 기록하는 것만으로 대부분의 V3 진행도를 얻고, 퓨전만 선택형 놀이로 즐긴다.

V3는 다음 기능을 한 번에 제공한다.

- 지역 음식 지도
- 계절 한정 음식
- 음식 세트 도감
- 음식 퓨전
- 음식 컬렉션 필터
- 카드 스킨
- 배경 수집
- 이벤트 카드
- Supabase 기반 사용자별 동기화

## 제품 원칙

1. 첫 실행에 가입이나 로그인 화면을 표시하지 않는다.
2. 식사 기록 한 번으로 카드, 지역, 계절, 세트 진행도를 함께 갱신한다.
3. 퓨전에서 원본 카드를 소모하지 않는다.
4. 스킨과 배경은 능력치를 바꾸지 않는 꾸미기 보상으로 제한한다.
5. 이벤트 핵심 보상은 조건 달성 시 확정 지급하며 무작위 확률만으로 제한하지 않는다.
6. 네트워크가 끊겨도 식사 기록을 잃지 않는다.
7. 기존 IndexedDB 데이터는 Supabase 이전 성공을 확인하기 전까지 삭제하지 않는다.

## 기술 방향

### 콘텐츠와 진행 데이터 분리

지역, 계절, 세트, 퓨전 조합, 스킨, 배경, 이벤트 정의는 TypeScript 콘텐츠 카탈로그로 관리한다. 사용자별 식사 기록, 카드, 보상, 퓨전 이력은 Supabase에 저장한다.

이 방식은 V3 규모에서 별도 관리자 화면을 만들 필요가 없고, 콘텐츠 규칙을 테스트와 코드 리뷰로 검증할 수 있다. 향후 운영자가 앱 배포 없이 콘텐츠를 자주 수정해야 하는 시점에만 카탈로그를 Supabase 관리 테이블로 이전한다.

### 클라이언트 구성

- React, TypeScript, Vite
- `@supabase/supabase-js`
- 기존 IndexedDB 저장소를 오프라인 대기열과 마이그레이션 원본으로 재사용
- Vercel 정적 배포
- Node.js 22 이상

브라우저에는 Supabase 프로젝트 URL과 publishable key만 제공한다. secret key 또는 service role key는 포함하지 않는다.

## 사용자 식별

첫 실행 시 기존 Supabase 세션이 없으면 `signInAnonymously()`를 호출한다. 사용자는 로그인 화면을 거치지 않고 즉시 기록을 시작한다.

익명 사용자도 고유한 사용자 ID와 세션을 가지며, 모든 사용자 데이터는 이 ID로 분리한다. 설정 화면에는 `내 도감 안전하게 보관하기` 항목을 제공해 익명 계정에 이메일을 연결할 수 있게 한다.

익명 상태에서 로그아웃하거나 브라우저 데이터를 삭제하거나 다른 기기를 사용하면 같은 계정으로 복구할 수 없다는 점을 계정 보호 화면에서 명확히 알린다. 익명 가입 남용 방지를 위해 Supabase 익명 로그인 제한과 CAPTCHA 적용을 배포 체크리스트에 포함한다.

- 플레이어 레벨과 XP

### 도감

- 세계지도: 지역별 발견 수와 완성률

- 꾸미기 보관함: 획득한 스킨과 배경 확인 및 적용

## V3 게임 규칙

### 지역 음식 지도

음식 카드에는 하나의 지역 ID가 있다. 음식 분류와 카드 획득 결과를 기반으로 해당 지역의 발견 수와 완성률을 계산한다. 초기 지역은 한식, 중식, 일식, 양식, 간식섬으로 구성한다.

각 지역은 잠긴 장소 목록을 실루엣으로 보여 주고, 첫 카드를 획득하면 지역을 밝힌다. 완성률은 고유 카드 종류 기준으로 계산해 같은 음식 반복 기록으로 부풀려지지 않게 한다.

### 계절 한정 음식

카드에는 선택적으로 계절 ID가 있다. 현재 날짜에 활성화된 계절 음식은 기록 결과에서 시즌 도장을 제공한다. 놓친 음식은 다음 연도의 동일 계절에 다시 등장하며 영구적으로 획득 불가능한 카드를 만들지 않는다.

초기 계절은 봄, 여름, 가을, 겨울 네 종류이며, 한국 시간대를 기준으로 판정한다.

### 음식 세트 도감

세트는 필요한 고유 음식 종류의 목록으로 정의한다. 사용자가 마지막 조건을 충족하면 세트를 자동 완성하고 보상을 한 번만 지급한다.

초기 세트 예시는 다음과 같다.

- 분식 탐험대: 라면, 밥, 간식
- 햇살 한입단: 과일, 음료
- 포근한 아침: 빵, 과일, 음료

보상은 코인, 스킨 또는 배경이며 중복 지급하지 않는다.

### 음식 퓨전

사용자는 보유 카드 두 장을 선택한다. 정해진 조합이 있으면 해당 퓨전 카드를 획득하고, 없으면 발견 힌트를 제공한다.

퓨전은 원본 카드를 삭제하거나 수량을 차감하지 않는다. 같은 퓨전 결과는 도감에 한 번만 신규 등록되며, 이후 시도는 연출만 다시 볼 수 있다.

### 컬렉션 필터

카드 목록은 지역, 계절, 세트, 희귀도 조건으로 필터링한다. 필터 결과가 없으면 잠금 해제 방법 또는 다른 필터 선택 안내를 보여 준다.

### 스킨과 배경

스킨과 배경은 세트, 시즌, 이벤트 보상으로 획득한다. 사용자는 보유한 꾸미기 항목을 카드에 적용할 수 있다. 꾸미기 항목은 희귀도, XP 또는 획득 확률을 변경하지 않는다.

### 이벤트 카드

이벤트는 시작·종료 시각, 달성 조건, 확정 보상 카드로 정의한다. 이벤트 기간에 조건을 충족하면 보상을 한 번만 지급한다. 기간이 끝나기 전에 남은 시간을 홈에서 표시한다.

## 데이터 모델

### `profiles`

- `user_id uuid primary key references auth.users`
- `nickname text`
- `level integer`
- `total_xp integer`
- `coins integer`
- `current_streak integer`
- `last_recorded_on date`
- `created_at timestamptz`
- `updated_at timestamptz`

### `meal_records`

- `id uuid primary key`
- `user_id uuid references auth.users`
- `food_type text`
- `amount text`
- `recorded_at timestamptz`
- `photo_path text`
- `client_created_at timestamptz`
- `created_at timestamptz`

`id`는 클라이언트가 기록 시작 시 생성한다. 재시도에도 같은 ID를 사용해 중복 저장을 막는다.

### `food_cards`

- `id uuid primary key`
- `user_id uuid references auth.users`
- `meal_id uuid references meal_records`
- `catalog_id text`
- `name text`
- `rarity text`
- `quote text`
- `xp integer`
- `region_id text`
- `season_id text nullable`
- `evolution_stage integer`
- `skin_id text nullable`
- `background_id text nullable`
- `created_at timestamptz`

### `user_rewards`

- `id uuid primary key`
- `user_id uuid references auth.users`
- `reward_type text`
- `reward_id text`
- `source_type text`
- `source_id text`
- `unlocked_at timestamptz`

`user_id`, `reward_type`, `reward_id`에 고유 제약을 둬 동일 보상을 한 번만 지급한다.

### `fusion_history`

- `id uuid primary key`
- `user_id uuid references auth.users`
- `left_card_id uuid references food_cards`
- `right_card_id uuid references food_cards`
- `fusion_catalog_id text`
- `created_at timestamptz`

## 보안

공개 스키마의 모든 앱 테이블에 RLS를 활성화한다. `SELECT`, `INSERT`, `UPDATE`, `DELETE` 정책은 모두 `(select auth.uid()) = user_id` 소유권 조건을 사용한다. UPDATE 정책에는 `USING`과 `WITH CHECK`를 모두 둔다.

2026년 신규 Supabase 프로젝트는 public 테이블이 Data API에 자동 노출되지 않을 수 있으므로 앱이 사용하는 테이블에만 `authenticated` 역할의 권한을 명시적으로 부여한다.

식사 사진은 비공개 `meal-photos` 버킷에 `{user_id}/{meal_id}/original` 경로로 저장한다. Storage 정책은 경로의 첫 폴더와 `auth.uid()`가 일치할 때만 읽기와 쓰기를 허용한다. 덮어쓰기가 필요한 경우 INSERT, SELECT, UPDATE 정책을 함께 제공한다.

## 저장과 동기화

식사 기록을 시작하면 클라이언트에서 UUID를 먼저 생성하고 IndexedDB에 `pending` 상태로 저장한다. 온라인이면 다음 순서로 처리한다.

1. 사진을 Storage에 업로드한다.
2. `meal_records`를 같은 UUID로 upsert한다.
3. 생성된 카드와 보상을 저장한다.
4. 로컬 항목을 `synced`로 표시한다.
5. 지역, 계절, 세트 진행 결과를 화면에 표시한다.

사진 업로드가 실패해도 식사 메타데이터와 카드는 로컬에 유지한다. 사용자는 전체 기록을 다시 만들지 않고 사진 업로드만 재시도할 수 있다.

보상 계산 함수는 동일한 식사와 사용자 상태에 대해 같은 결과를 내는 순수 함수로 작성한다. 데이터베이스 고유 제약과 고정 식사 ID를 함께 사용해 재시도 시 XP, 카드, 보상이 중복 지급되지 않게 한다.

## 기존 데이터 이전

기존 IndexedDB에 카드가 있고 Supabase 이전 완료 표시가 없으면 마이그레이션 안내를 표시한다. 사용자가 진행하면 기존 식사와 카드를 사용자 ID에 연결해 순서대로 업로드한다.

모든 대상 건의 업로드와 재조회가 성공한 후에만 `migration_complete`를 기록한다. 기존 로컬 데이터는 자동 삭제하지 않으며, 이후 별도의 저장 공간 정리 기능에서 사용자가 삭제하도록 한다.

## 오류 처리

- 익명 인증 실패: 로컬 모드로 진입하고 상단에 동기화 대기 상태를 표시한다.
- 데이터 불러오기 실패: 마지막 로컬 데이터를 표시하고 다시 불러오기 버튼을 제공한다.
- 사진 업로드 실패: 카드와 식사 정보는 보존하고 사진만 다시 업로드할 수 있게 한다.
- 세션 만료: 세션 갱신을 한 번 시도하고 실패하면 로컬 대기열을 유지한다.
- 콘텐츠 카탈로그 불일치: 알 수 없는 ID를 삭제하지 않고 기본 카드 표현으로 표시한다.
- 중복 요청: 고정 UUID와 데이터베이스 고유 제약으로 같은 결과를 반환한다.

## 테스트와 검증

### 단위 테스트

- 지역 완성률은 고유 음식 기준으로 계산된다.
- 활성 계절은 한국 시간 기준으로 결정된다.
- 세트 보상은 조건 충족 시 한 번만 생성된다.
- 퓨전 원본 카드는 유지된다.
- 알려지지 않은 조합은 힌트를 반환한다.
- 재시도해도 카드와 보상 결과가 중복되지 않는다.

### 저장소 테스트

- 익명 사용자 A는 사용자 B의 행을 읽거나 수정할 수 없다.
- Storage 경로 소유자가 아닌 사용자는 사진에 접근할 수 없다.
- 오프라인 기록은 재연결 후 한 번만 저장된다.
- IndexedDB 마이그레이션은 일부 실패 후 안전하게 재시도된다.

### 화면 테스트

- 하단 네 메뉴와 도감 내부 탭을 키보드로 조작할 수 있다.
- 필터와 빈 결과 안내가 올바르게 표시된다.
- 퓨전 선택, 결과 공개, 꾸미기 적용 흐름이 동작한다.
- 모바일 너비에서 가로 스크롤 없이 사용할 수 있다.

### 배포 검증

- `npm run test:run`
- `npm run build`
- Supabase 데이터베이스 보안 검사
- Vercel Preview 배포 확인
- 익명 신규 사용자와 기존 IndexedDB 사용자 각각의 전체 기록 흐름 확인

## 완료 기준

1. 사용자가 로그인 화면 없이 앱을 시작할 수 있다.
2. 서로 다른 사용자 데이터와 사진이 섞이지 않는다.
3. 식사 기록 한 번으로 카드, 지역, 계절, 세트 진행도가 자동 반영된다.
4. 퓨전, 스킨, 배경, 이벤트 카드가 실제 저장되고 새로고침 후 유지된다.
5. 오프라인이나 업로드 실패 후 기록을 잃지 않고 재시도할 수 있다.
6. 기존 V2 데이터가 중복 없이 Supabase로 이전된다.
7. 테스트와 프로덕션 빌드가 통과하고 Vercel에서 모바일로 확인할 수 있다.
